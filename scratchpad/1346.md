# Add focus-visible ring to the two reader mobile nav toggles

Status: pending
Tags: `frontend`, `a11y`
Depends on: None
Blocks: —

## Scope

Follow-up from #1338. Two sibling reader mobile drawer toggles render the same native `<button id="sidebar-toggle-btn">` control but only carry a `hover:` state — neither has a keyboard `focus-visible:` ring. Add the canonical #1224 accent focus ring (and the 44px minimum tap target from the design-system button contract) to BOTH toggles so keyboard and consistency stay aligned.

Owning partials (both are indexed reader partials, see `_docs/design-system.md` Partials and Component Index):

- `templates/content/reader/_mobile_nav_toggle_gated.html` — the gated-safe toggle (issue #1338).
- `templates/content/reader/_mobile_progress_bar.html` — the ungated progress + drawer toggle (issue #517).

Both buttons currently share this exact class string:

```
w-full flex items-center justify-between rounded-lg border border-border bg-card px-4 py-2.5 text-sm font-medium text-foreground transition-colors hover:bg-muted
```

Change: append the canonical #1224 focus-ring set plus `min-h-[44px]` to each button's `class`, so both become:

```
w-full flex items-center justify-between rounded-lg border border-border bg-card px-4 py-2.5 min-h-[44px] text-sm font-medium text-foreground transition-colors hover:bg-muted focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-accent focus-visible:ring-offset-2 focus-visible:ring-offset-background
```

Do not change any `id`, `data-testid`, `aria-*`, icon, or label. This is a class-string-only change to the `<button>` on each partial. Keep the two class strings identical to each other so the siblings do not drift again.

No model, view, URL, or API surface is involved — this is a static template class edit. No API acceptance criteria apply.

- [ ] The `<button id="sidebar-toggle-btn">` in `templates/content/reader/_mobile_progress_bar.html` includes the same focus-ring class set.

## Test Scenarios

### Django template render (regression guard)
A focused Django test (in `content/tests/`) renders a workshop tutorial page for a gated/anonymous visitor and asserts the mobile toggle button markup contains `focus-visible:ring-accent`. If a course reader test already exercises `_mobile_progress_bar.html`, add the same assertion there. These guard against the ring being dropped again.

### Scenario: Keyboard user tabs to the mobile drawer toggle on a gated workshop
Given: An anonymous visitor on a phone-width viewport opens a gated workshop tutorial page (renders `_mobile_nav_toggle_gated.html`)
1. Press Tab until focus reaches the "Workshop Navigation" drawer toggle
Then: A visible accent focus ring appears around the toggle button (not just the default browser outline)
2. Press Enter
Then: The shared `#sidebar-nav` page-navigation drawer opens

### Scenario: Keyboard user tabs to the mobile progress toggle on an ungated reader
Given: A logged-in member on a phone-width viewport opens an ungated course/workshop reader (renders `_mobile_progress_bar.html`)
1. Press Tab until focus reaches the "Page N of M" drawer toggle
Then: The same visible accent focus ring appears around the toggle button
2. Press Enter
Then: The `#sidebar-nav` drawer opens and the progress bar still shows position

Note: keyboard focus-ring appearance is best covered by a Playwright test asserting the class is present on focus; the visual crispness of the ring is `[HUMAN]` visual judgment and does not block.
