## Background

Follow-up from #1308 (recurring Stripe-to-website subscription reconciliation). Two acceptance criteria on #1308 are still unchecked:

1. "Extends the existing tier-reconcile API and OpenAPI schema with all documented state fields, filters, cursor/cap behavior, run enqueue/history/detail endpoints, stable error shapes, and staff-token authorization before Stripe/task work."
2. "The Playwright scenarios below pass without contacting live Stripe."

Grooming finding (verified against the code):

- The `tier` / `classification` / cursor filters were intentionally rescoped during #1308 implementation. `GET /api/payments/tier-reconcile/diagnostics` (`api/views/tier_reconcile.py`) stays backward-compatible and only supports `email` and `include=ok`. The new filters actually landed on `GET /api/payments/tier-reconcile/runs/<uuid>` (`reconciliation_run_detail` in `api/views/subscription_reconciliation.py`), which supports `classification`, `tier`, `filter=actionable|scheduled|...`, `page`/`page_size`, and returns `next_cursor`. The `runs` list endpoint supports `page`/`next_cursor`. So the capability EXISTS — it just lives on the `runs` endpoints, not on `/diagnostics`.
- Gap found: the `runs` and `runs/<uuid>` views have NO `@extend_schema` decorators, so these filters and the enqueue/history/detail endpoints are undocumented in OpenAPI (`_docs/openapi.json`). `_docs/api.md` and `_docs/studio-user-statuses.md` do not mention the `runs` endpoints or their filters.
- Only 2 of the 12 #1308 Playwright scenarios are scripted (`playwright_tests/test_subscription_reconciliation_1308.py`: `test_operator_reviews_scheduled_ended_and_dunning`, `test_read_only_check_queues_without_changing_access`). The other 10 are claimed to be covered by Django tests but are not mapped or verified.

This issue does two things: (1) resolve the diagnostics-filter AC as satisfied-by-rescope by documenting the `runs` endpoints properly, and (2) close the Playwright-coverage AC by scripting the high-value operator UI journeys and formally mapping the rest to their Django-test equivalents.

## Scope

Decision: this is NOT adding filters to `/diagnostics`. `/diagnostics` stays backward-compatible (`email`, `include=ok` only). The rescope is accepted. The work is documentation/OpenAPI + Playwright coverage, plus amending the #1308 AC wording.

### 1. OpenAPI + docs for the runs endpoints

- Add `@extend_schema` to `reconciliation_runs_dispatch` (GET history / POST enqueue) and `reconciliation_run_detail` in `api/views/subscription_reconciliation.py`, documenting: staff-token auth; `GET runs` pagination (`page`, `page_size`, `next_cursor`); `POST runs` enqueue returning `202` with run id/status and accepting no apply mode; `GET runs/<uuid>` filters `classification`, `tier=basic|main|premium`, `filter`, pagination, `next_cursor`; the finding/run field shapes; and the project-standard 422 for invalid `classification`/`tier` and 401 for missing/non-staff tokens.
- Regenerate/refresh `_docs/openapi.json` so the `runs` endpoints appear.
- Update `_docs/api.md` and `_docs/studio-user-statuses.md`: document that live-check tier/classification filtering is done via the persisted `runs` endpoints (and the Studio report), that `/diagnostics` remains the synchronous backward-compatible email/`include=ok` live check, and give concrete `curl` examples for `runs`, `runs/<uuid>?classification=...&tier=main`, and pagination via `next_cursor`.

### 2. Playwright coverage for the remaining #1308 scenarios

Using deterministic pre-seeded/mocked reconciliation state (never live Stripe), script the operator UI journeys that are genuinely end-to-end through the Studio report and are not already covered by the 2 landed tests. Prioritize these #1308 scenarios (they exercise the Studio report/filters/links, which Django view tests cannot fully assert as a user flow):

- Operator reviews cancellation drift across Basic, Main, and Premium (tier filter round-trip in the report).
- Operator finds an immediate cancellation missed by webhooks (Actionable filter, `Revert to Free` label, member link).
- Scheduled cancellation becomes ended on a later run (run-history comparison).
- Operator finds duplicate Stripe ownership before any account is changed (blocked-apply visibility).
- Operator distinguishes a missed deletion webhook from a processing failure (webhook-evidence display).
- Operator gets a useful clean report (no-findings empty state).
- Operator can distinguish reconciliation from checkout identity mismatches (navigation copy distinct from Payment mismatches).
- Unauthorized member cannot inspect or run reconciliation (non-staff redirect/403).

For the API-only / non-UI scenarios that are legitimately better as Django/API tests (e.g. "Operator safely previews and explicitly applies selected canceled members through the API", "Operator distinguishes payment failure from cancellation"), do NOT force a brittle Playwright test — instead add an explicit mapping comment/table in `playwright_tests/test_subscription_reconciliation_1308.py` (or the issue) naming the covering Django test in `payments/tests/` or `api/tests/`, so the reviewer can confirm each of the 12 scenarios has a home.

Follow `_docs/testing-guidelines.md`: no skipped/flag-gated tests, assert on specific report rows/testids, never contact live Stripe.

### 3. Amend #1308 acceptance criteria

- Reword the #1308 "Extends the existing tier-reconcile API..." AC so it points at the `runs`/`runs/<uuid>` endpoints for tier/classification/cursor filters (with `/diagnostics` explicitly backward-compatible), then check it off once OpenAPI/docs land.
- Check off the #1308 "Playwright scenarios below pass" AC once the scenarios above are scripted and the Django-mapping is documented.

### Out of scope

- Adding tier/classification/cursor filters to `/diagnostics` (rescope is accepted; it stays backward-compatible).
- Any change to reconciliation classification logic, apply semantics, the daily schedule, or the Studio apply guard — those shipped in #1308 and are not touched here.

## Playwright Test Scenarios

### Scenario: Operator filters the reconciliation report by paid tier
Given: A staff user is logged in and a completed run has one stale canceled member in each of Basic, Main, and Premium
1. Navigate to `/studio/payments/subscription-reconciliation/` and open the latest run
2. Filter by Main
Then: Only the Main-tier stale member row is shown, with its Main website tier and Stripe status
3. Filter by Premium
Then: Only the Premium-tier row is shown; no paid tier is missing across the filters

### Scenario: Operator finds an immediate cancellation missed by webhooks
Given: A Main member is paid on the website but the seeded Stripe state is `canceled` with no processed deletion event
1. Open the latest run and apply the Actionable filter
Then: The member appears as `Ended subscription still entitled` with proposed action `Revert to Free` and a suspected-missed-deletion webhook badge
2. Click the member link
Then: The Studio member detail opens with Stripe context

### Scenario: Operator sees duplicate Stripe ownership is blocked from apply
Given: Two local users share one seeded `stripe_customer_id`
1. Open the latest run and view both affected rows
Then: Both are labeled `duplicate_stripe_ownership`, list the conflicting accounts, and show no apply/revert action

### Scenario: Operator reads a clean no-findings report
Given: A completed run where every seeded member is in sync
1. Open the latest run
Then: A helpful "no findings / everyone in sync" empty state is shown, not a blank table, and summary counts still render

### Scenario: Non-staff member cannot open or run reconciliation
Given: A logged-in non-staff member
1. Navigate to `/studio/payments/subscription-reconciliation/`
Then: Access is denied (redirect to login or 403), and the read-only check cannot be triggered

### Scenario: Operator distinguishes reconciliation from checkout identity mismatches
Given: A staff user on the Payments/Users operator navigation
1. Open the navigation near Payment mismatches
Then: The subscription-reconciliation report link and the checkout Payment-mismatches link are visibly distinct tools with copy that explains the difference
